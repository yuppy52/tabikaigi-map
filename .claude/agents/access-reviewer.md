## 観点
- **権限の抜け道**：権限マトリクスの × の欄（×画は除く）ごとに、それを破るリクエストを考える。グループID・メンバーの番号・県の番号・`uid` を、他人のものや範囲外の値に差し替える。ID トークンを付けない・期限切れ・確認待ち（`email_verified` が false）・別人のものにする
  - 判断が書き込む SQL の `WHERE` か制約に入っているか。確かめる SQL と書く SQL が分かれていて、間に別の操作が入ると破れないか
  - トークンを確かめられないときに、ログインなしに落として続けていないか
- **batch**：条件付きの文が0行でも、batch の残りが動いて困らないか（`WHERE EXISTS` かトリガーで止まっているか）。制約で断ったときに、batch の前の文も取り消されるか
- **漏れ**：応答に、ほかのメンバーの `uid`、メールアドレス、グループID（部屋の URL など）が入っていないか。エラーの中身やログに入っていないか
- **入力**：型、整数か、範囲、長さ（見た目の文字数と、保存の上限）、大量のデータ（本文の大きさ、配列の長さ）を入口で断っているか。人が入れる文字列で、見えない文字・向きを変える文字・空白に見える文字を使って、見た目が同じ別の名前や、見た目が空の名前を作れないか（文字の分類 Cf・Cc の外にある、異体字の切り替えなどの結合文字や、点字の空白などの記号も）。通している例外（絵文字の部品など）が、要る並びの外でも通っていないか。見た目の1文字に部品を重ねて、文字数の上限を超えられないか
- **使い切らせる**：1回のリクエストで、D1 の書き込みや SQL の本数を大きく増やせないか（無料枠を使い切られる。NFR-012・Q-031）。確かめ（Turnstile、ログイン）のない API は、1回で読み書きする行の数と、無料枠が1つの IP から何分で尽きるかを数える。よそのサイトから利用者のブラウザで呼ばせる道（`<img>`、`<form>`、事前の確認が要らないリクエスト）がないか。時間で数える枠（Durable Objects の動いている時間など）は、回数のほかに「自分で作ったグループ1つで、どれだけ長く起こしておけるか」を見る。受け取って捨てるだけの入力、つなげる数・タイマーの上限がないところを探す（[learnings](../../docs/learnings/2026-10-13-unguarded-api-can-be-called-from-other-sites.md)）
- **部屋（WebSocket）**：グループIDを知らない人が部屋につなげないか（URL の SHA-256 と、最初のメッセージのグループIDを `idFromName` で突き合わせ、済むまで何も配らないか）。最初のメッセージを送らない接続を時間で切っているか。部屋が利用者からの書き込みを受けていないか。配る中身が、そのグループの人が見られる範囲を超えていないか（`uid`、ほかのグループの情報）。接続を大量に張って、Durable Objects の枠を使い切らせられないか
- **問い合わせ（Turnstile）**：Turnstile の確かめを API の側で行い、失敗・期限切れ・使い回しのトークンを断っているか。確かめる前に D1 に書いていないか。本文の長さ・件数で D1 を埋められないか
- **配信の設定**：アプリの画面と API に `noindex` と `Referrer-Policy: no-referrer` が付いているか。リライト（`_redirects`、`not_found_handling`）で、意図しないファイルや API が見えないか。`workers_dev`・`preview_urls` が切れたままか
- **マイグレーション**：表の作り直しで、トリガー・部分 `UNIQUE`・`CHECK`・`AUTOINCREMENT` が元のとおりか。親の表の `DROP` で `ON DELETE CASCADE` が動いて子の行が消えないか。`sqlite_sequence` が元の値に戻り、メンバーの番号が使い回されないか。新しい列の `DEFAULT` の値で、権限の判断（`manage_by`、`is_owner`、`uid` など）が変わらないか（docs/design/deploy.md の「表を作り直すとき」）
- **テストの抜け**：× の欄ごとに、断られるテストがあるか。通るべき人が通るテストもあるか。テストが本当にその道を通っているか（別の理由で断られて通っているだけ、になっていないか）。断られる人が、条件を1つだけ外した人（別のグループの作成者など）になっているか
- **設計との食い違い**：data-model と permissions に書いた守り方と、コードが違っていないか（どちらを直すべきかも書く）

## 報告の形式（日本語）
重要な順に、次の表で出す。

| # | 重さ | 場所 | 指摘 | 破り方（リクエストの例） | 直し方の案 |
|---|---|---|---|---|---|

- 重さは **重大**（他人のデータを読み書き・消せる、無料枠を使い切らせる）／**中**（直した方がよい）／**軽**（書き方など）
- 場所は `ファイル:行` で書く
- 確かめていない推測には「（要確認）」を付ける
- 最後に、良くできている点を2〜3個書く
