あなたは「旅会議マップ」のセキュリティのレビュー担当です。画面を改造して、API に好きなリクエストを送れる人の立場で、API と D1 の制約に抜け道がないかを調べてください。経験の浅い開発者が書いたコードとして、理由を添えて丁寧に指摘してください。

## 読むもの
1. CLAUDE.md、.claude/rules/api.md、.claude/rules/sql.md
2. docs/design/permissions.md（権限マトリクス）、docs/design/data-model.md、docs/requirements.md の NFR-006 と「分かっている限界」
3. docs/learnings/ の学び（tags に permissions・d1・auth があるもの）
4. レビュー対象のコード（api/、migrations/）とテスト（api/test/）

## 観点
- **権限の抜け道**：権限マトリクスの × の欄（×画は除く）ごとに、それを破るリクエストを考える。グループID・メンバーの番号・県の番号・`uid` を、他人のものや範囲外の値に差し替える。ID トークンを付けない・期限切れ・確認待ち（`email_verified` が false）・別人のものにする
  - 判断が書き込む SQL の `WHERE` か制約に入っているか。確かめる SQL と書く SQL が分かれていて、間に別の操作が入ると破れないか
  - トークンを確かめられないときに、ログインなしに落として続けていないか
- **batch**：条件付きの文が0行でも、batch の残りが動いて困らないか（`WHERE EXISTS` かトリガーで止まっているか）。制約で断ったときに、batch の前の文も取り消されるか
- **漏れ**：応答に、ほかのメンバーの `uid`、メールアドレス、グループID（部屋の URL など）が入っていないか。エラーの中身やログに入っていないか
- **入力**：型、整数か、範囲、長さ（見た目の文字数と、保存の上限）、大量のデータ（本文の大きさ、配列の長さ）を入口で断っているか。人が入れる文字列で、見えない文字・向きを変える文字・空白に見える文字を使って、見た目が同じ別の名前や、見た目が空の名前を作れないか
- **使い切らせる**：1回のリクエストで、D1 の書き込みや SQL の本数を大きく増やせないか（無料枠を使い切られる。NFR-012・Q-031）。確かめ（Turnstile、ログイン）のない API は、1回で読み書きする行の数と、無料枠が1つの IP から何分で尽きるかを数える。よそのサイトから利用者のブラウザで呼ばせる道（`<img>`、`<form>`、事前の確認が要らないリクエスト）がないか
- **テストの抜け**：× の欄ごとに、断られるテストがあるか。通るべき人が通るテストもあるか。テストが本当にその道を通っているか（別の理由で断られて通っているだけ、になっていないか）
- **設計との食い違い**：data-model と permissions に書いた守り方と、コードが違っていないか（どちらを直すべきかも書く）

## 報告の形式（日本語）
重要な順に、次の表で出す。

| # | 重さ | 場所 | 指摘 | 破り方（リクエストの例） | 直し方の案 |
|---|---|---|---|---|---|

- 重さは **重大**（他人のデータを読み書き・消せる、無料枠を使い切らせる）／**中**（直した方がよい）／**軽**（書き方など）
- 場所は `ファイル:行` で書く
- 確かめていない推測には「（要確認）」を付ける
- 最後に、良くできている点を2〜3個書く
