# ドキュメントの書き方

docs/ 以下を書く・直すときのルール。全体の構成と書き分けは [docs/README.md](../../docs/README.md) に従う。

## 言葉
- 日本語で書く。利用者が読む requirements では技術の言葉をなるべく使わない
- requirements では、全員に当てはまる決まりを、特定の使い方（ログインなし／あり）の節の中に書かない。共通の節に置く
- 用語は用語集（`docs/glossary.md`、作成後）の言葉にそろえる。新しい言葉が必要なら用語集に先に足す

## 要件ID
- 機能要件は `REQ-001`、非機能要件は `NFR-001` の形式で番号を振る。一度振った番号は振り直さない（削除したら欠番にする）
- design や adr で要件に対応する箇所には、対応する要件IDを書く（例：`（REQ-012）`）

## 状態
- 各ドキュメントの先頭に「状態：下書き／レビュー待ち／確定」を書く
- 「確定」のドキュメントを変えたら、状態を「レビュー待ち」に戻し、変えた理由を一言残す

## 図
- ER図、シーケンス図、遷移図などは Mermaid で Markdown の中に書く（これが正本）
- アイコンや配置に意味がある図（システム構成図、ワイヤーフレーム）は draw.io で作り、`docs/**/*.drawio.svg` として保存する

## 未確認のこと
- 調べきれていない事実は「（要確認）」と書き、推測で断定しない
- 外部の事実（料金、制限、仕様）を書くときは、出典のURLを残す

## 決めたことの反映
- ユーザーと何かを決めたら、同じ論点を書いている他のドキュメントを `grep` で探し、同じ変更の中で直す
- 決定でなくても、推奨や前提が変わったら（提案中の ADR の推奨が変わった、前提が訂正された）、古い前提を表す言葉で `grep` し、同じ変更の中で直すか「〜の時点の判断」と注記する。まだ書き直さない文書には、冒頭に「どの前提の版か」と「いつ書き直すか」を書く
- `grep` に加えて、`open-questions.md` の「影響先」の列をチェックリストにし、書かれたドキュメントを1つずつ開いて確かめる（Mermaid の図は文章とちがう言葉で書かれていることが多いので、分岐を目で追う）
- 未決事項は `docs/open-questions.md` で一本化して管理する。各ドキュメントには「（要確認：Q-001）」と書いて参照する
- 決めた論点は、`open-questions.md` の状態を「決定」にして反映先を書き、他のドキュメントの「要確認」を消す
