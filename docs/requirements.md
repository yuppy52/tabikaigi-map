## この文書について

- 利用者から見た「何ができるか」を書く。どう作るかは [design/](design/) に書く
- 機能要件は `REQ-001`、非機能要件は `NFR-001` の形で番号を振る。**一度振った番号は振り直さない**（なくした要件は欠番にする）。あとから足した要件は、番号の順ではなく、内容の合う節に置く。design や adr からは「（REQ-012）」のように参照する
- 「UC」の列は、元になった [ユースケース](use-cases.md) の番号
- 言葉は [用語集](glossary.md) にそろえる。決まっていないことは「（要確認：Q-xxx）」と書き、[open-questions.md](open-questions.md) で管理する

## 目的

友達グループで「今まで行ったことのある都道府県」を日本地図に塗って共有し、全員まだ行っていない県を見つけて、次の旅行先を決めやすくする。

## 利用者

- 友達同士の小さなグループ（1グループ最大20人）
- スマホで使う。招待URLは主に LINE で送られる
- 運営者（このアプリを作って動かす人。1人）

## 2つの使い方

ログインせずに名前だけで使うこともでき、ログインして使うこともできる。違いのまとめ（決まりの正本は各要件）：

| | ログインなし | ログインあり |
|---|---|---|
| 入り方 | グループごとの招待URL（REQ-004） | 招待URL、またはグループ一覧（REQ-032） |
| 名前 | グループごとに入力する（REQ-007） | 同じ |
| 名前の変更 | できない（REQ-015） | 本人だけできる（REQ-014） |
| グループの切り替え | なし（REQ-026） | あり（REQ-032） |
| 「行った」 | グループのメンバーごとに持つ（REQ-023） | アカウントに保存し、全グループに同期する（REQ-030） |
| 「行った」を編集できる人 | そのグループの誰でも（REQ-022） | 本人だけ（REQ-031） |

| REQ-040 | 同じ端末からログインなしで参加していた他のグループは、ログインしたときには何もしない。あとでそのグループを開いたとき、端末が覚えているメンバーがいて紐づいていなければ、REQ-037 と同じく本人確認なしで紐づけ、「行った」は REQ-038 で扱う。そのグループに自分のアカウントのメンバーがすでにいれば REQ-039 と同じに扱う。端末が何も覚えていなければ、REQ-041〜REQ-043 の流れになる | UC-08・UC-02 |

REQ-038 の扱い。グループでの「行った」を G、アカウントの「行った」を U とする。

| 状況 | 挙動 |
|---|---|
| U が空（このアカウントでまだ「行った」を保存していない） | 確認なしで G をアカウントに引き継ぐ |
| G が U にすべて含まれている | 確認なしで U を表示する |
| それ以外 | 確認を出す（下） |

> アカウントに保存されている「行った」（N県）をこのグループに反映しますか？
> - **アカウントのデータを使う**：このグループでの入力は破棄する
> - **合算する**：G と U を合わせてアカウントに保存する（参加中の他のグループにも反映される）

### 分かっている限界（信頼ベースのため受け入れる）

- 本人確認（REQ-043）は自己申告で、本当に本人かは確かめていない。ログインしていない作成者のメンバーを、先に別の人が自分のものにすると、その人が作成者になる。ただし初期値の「誰でも」では、もともと誰でもメンバーやグループを削除できるので、増える被害は「作成者のみ」に変えてほかの人を締め出せることだけ。起きたらグループを作り直してもらう
- メンバーを削除しても、招待URLは変わらない（再発行しない）ので、その人はまた参加できる。削除は「追い出す」ためのものではない
- ログインしていないメンバーは、「作成者のみ」の設定でも、その名前で入れば誰でも退出させられる（本人を区別できないため。2026-10-10 に Q-018 で決定。紐づいたメンバーは本人しか退出させられない）
- 作成者が別の端末から別の名前で入り、そちらをアカウントに紐づけると、作成者のメンバーはログインなしのまま残る（REQ-039）。その間は「作成者のみ」にできない（元の作成者のメンバーの名前で入っても、「誰でも」の操作だけ）。戻すには、紐づいた別の名前のメンバーで退出してから、作成者のメンバーの名前で入り直して紐づける（REQ-043。アカウントの「行った」は残る）。ログアウトして作成者のメンバーで退出すると、作成者は戻らない（2026-10-11）
- 招待URL（グループID）を知っている人は、参加しなくても、ログインなしのメンバーにできることはすべてできる（地図とアカウントの「行った」を読む、リアルタイムの知らせを受ける、紐づいていないメンバーの「行った」の付け外しと退出、「誰でも」のときの管理の操作）。ログインなしの人は、保存先から見てメンバーかどうかを見分けられないため。招待URLを知っていれば参加して同じことができるので、増える被害はない（2026-10-11。[権限マトリクス](design/permissions.md)）
- 「作成者のみ」にした作成者が来なくなる（メールアドレスを失ってログインできない、など）と、そのグループはほかの誰も管理できず、削除もできない（作成者のメンバーは本人しか退出させられない）。運営者も手で戻さない。グループを作り直してもらう（2026-10-11 にユーザーと決めた）
- メールアドレスの確認が済んでいないアカウント（打ち間違えたアドレスで作った場合を含む）は、ログインありとして扱わないので、退会できない。そのアカウントは使うサービス（Firebase Authentication）に残る。運営者も消さない（2026-10-11 にユーザーと決めた。NFR-007 の「退会すれば自分の情報を消せる」の例外）
- 誰でも参加して書き込めるので、悪意のある人や不具合が無料枠を使い切ると、無料枠が戻るまで（翌日など）全員が使えなくなる（NFR-012）。請求は来ない。防ぐ手立てを入れるかは基本設計で決める（要確認：Q-031）
- 利用が増えて無料枠（1日あたりの回数など）を超えたときも、その日は保存やリアルタイムの反映が止まり、翌日に戻る。有料プランは上限なく請求が来るので使わない（NFR-004）。これを受け入れる（2026-10-04 にユーザーと決めた）。本当に利用が伸びたら、そのときに構成を考え直す
- 利用者が削除したグループやメンバーは、戻せない（NFR-017）。削除の前の確認で防ぐ
- 参加する前に見えるのはグループ名とメンバーの名前だけ（REQ-002）だが、これは画面の側の決まりで、保存先では守らない。改造した画面なら参加する前でも地図を読めるが、招待URLを知っていれば参加して見られるので、増える被害はない
- ログインした後に、端末が覚えているメンバーのグループを開くと、本人確認なしで紐づける（REQ-040）。そのため、1台を何人かで使う端末では、前に別の人がログインなしで入ったメンバーを、ログインした人のアカウントに紐づけてしまうことがある（例：A がログアウトした端末で B がログインなしで入り、そのあと A がログインし直してそのグループを開く）。ログインしたのは A なので、A のメンバーとして扱ってよいと判断した（2026-10-04）。共用の端末では、使い終わったら「メンバーを変更する」（REQ-056）で端末の記憶を消してもらう
- すでに使われているメールアドレスで登録しようとしたとき、出る文から、そのアドレスが登録済みだと分かりうる（REQ-058）。本当に隠すには自前でメールを送る仕組みが要るため、受け入れる（2026-10-04）。他人に登録済みだと知られて困るときは、パスワードの再設定（REQ-029）で守る
- メール＋パスワードで作ったアカウントが確認待ちのうちに、同じメールアドレスで Google でログインすると、パスワードでは入れなくなる（なりすまし対策として、使うサービスがパスワードを外すため。[auth-flow](design/auth-flow.md)）。パスワードで入りたいときは、再設定（REQ-029）で付け直す（2026-10-04）

| NFR-006 | 次のことは、画面を改造されても破られないように、データの保存先の側で守る。(1) 紐づいたメンバーの「行った」と名前は、本人しか変えられない（REQ-031・REQ-014）。(2) アカウントの「行った」とメールアドレスに書き込めるのは本人だけ。メールアドレスは本人だけが読める。アカウントの「行った」は、本人と、同じグループのメンバーが読める（地図に出すため。REQ-017・REQ-030。グループIDを知っていれば参加の前でも読める：「分かっている限界」）。(3) 紐づいたメンバーを別のアカウントに付け替えられない。紐づけられるのは自分のアカウントだけ（REQ-013・REQ-043）。(4) 管理できる人を変えられるのはログインしている作成者だけで、作成者を勝手に変えられない（REQ-045・REQ-052）。(5) 「作成者のみ」のときは、グループ名の変更、グループの削除、メンバーの削除を作成者しかできない（REQ-046〜REQ-048）。(6) 自分のアカウントは自分しか消せない（REQ-036）。(7) 参加していないグループを探したり一覧したりできず、グループIDを知らなければ中身を読めない（NFR-005）。(8) 1グループ20人まで、名前とグループ名の長さに上限がある（保存先は見た目の文字数より少し余裕のある上限で守る。REQ-005・REQ-009・REQ-010）。(9) 1つのグループで、1つのアカウントに紐づくメンバーは1人だけ（REQ-039）。(10) メールアドレスの確認が済んでいないアカウントは、ログインありとして扱わない（メンバーに紐づけられない、作成者として設定を変えられない。REQ-057）。(11) 1つのグループの中で、名前が重複しない（REQ-008。REQ-011 の決まりで同じとみなす名前も含む）。(12) 紐づいたメンバーは、本人しか退出させられない（REQ-049・Q-018。メンバーの削除は管理できる人の設定に従う）。(13) アカウントに紐づくメンバーは10グループまで（REQ-060）。(12)(13) は 2026-10-11 に足した。(9)(10) は 2026-10-04 に足した。(11) は、それまで保存先では守らない（Firestore のルールで書けないため）としていたが、案 C ならデータベースの制約で守れるので、2026-10-04 に守ることにした。保存先で守れるかは基本設計で確かめる（要確認：Q-019、[ADR 0003](adr/0003-backend-selection.md)）。保存先で守らないものは「分かっている限界」に書く |

### 運用

運営者が、アプリが使われているか、無料枠に収まっているか、壊れていないかを、友達からの報告を待たずに知るための要件。

| ID | 要件 |
|---|---|
| NFR-010 | **利用状況の把握**：運営者は、グループの数、メンバーの数（ログインあり・なし別）、最近使われたグループの数（例：直近30日に開かれた）を確かめられる。使われているかを知ることと、無料枠の見積もりに使う。人数や回数の集計で足り、利用者一人ひとりの行動は追わない。グループ名、メンバーの名前、誰がどこへ行ったか、**招待URL（グループID）**は、集計のために外部のサービスへ送らない（招待URLを知れば誰でも参加できるため。外部に送るページのURLからはグループIDを伏せる）（方法は要確認：Q-025） |
| NFR-011 | **無料枠の監視**：運営者は、使っているサービスの使用量が無料枠のどのくらいかを確かめられる。上限に近づいたら（例：8割）、運営者に知らせが届く。知らせを無料で作れないサービスなら、運営者が決まった頻度（例：週1回）で確かめる、で代えてよい（方法と数字は要確認：Q-026） |
| NFR-012 | **無料枠を超えたとき**：データの保存や読み込みが止まったときは、利用者に「いまは使えない」ことが分かる表示を出す（NFR-009）。止まる前に保存したデータは失われない。無料枠が戻れば（翌日・翌月など）、そのまま使える。画面の配信そのものが止まったときは表示を出せないので、この要件の対象外とする（Q-026） |
| NFR-013 | **エラーの把握**：利用者の画面で起きたエラー（保存の失敗、画面が動かないなど）を、運営者が把握できる。エラーの記録には、メンバーの名前、メールアドレス、行った都道府県、招待URL（グループID）を含めない（方法は要確認：Q-027） |
| NFR-014 | **運用の手間**：運営者1人で回せる形にする。ふだんの確認は短時間で済み、確かめる場所はできるだけ少なくまとめる（何かあったときは知らせが届き、そのときだけ詳しく見る）。MVP では運営者用の管理画面は作らず、使用量は使うサービスの管理画面と知らせで、利用状況は運営者が手元で動かす集計で確かめる。管理画面は MVP の次に作る（要確認：Q-030） |
| NFR-018 | **削除の依頼への対応**：利用者は、問い合わせ用のフォームから、データを消してほしいと頼める（運営者の個人のメールアドレスは公開しない）。フォームはアプリの中に作る（2026-10-04 にユーザーと決めた。外部のサービスに送らないので、プライバシーポリシーの送り先は増えない）。返事や確認のメールは、運営者の個人のアドレスではなく、このアプリ用に作ったアドレスから送る。本人の確かめ方：ログインありの人は、登録したメールアドレスに確認を送る。ログインなしの人は、招待URLとメンバーの名前を教えてもらえれば消す（招待URLを知っている人なら、アプリの中でも同じことができるため）。頼まれてから1か月以内に応じる。ふだんは利用者が自分で消せる（退会 REQ-036、退出 REQ-049）ので、これは例外のときのため |

## やらないこと（MVP）

- 招待URLの再発行
- グループごとに内容が変わるリンクのプレビュー（OGP は全グループ共通）
- 市区町村単位、訪問日、写真
- 行き先の投票などの「決める」機能
- 使われなくなったグループの自動削除。使われなくなったグループも残り続ける（最後の1人が退出したときにグループを削除するのは、退出の操作の一部として行う）
- メンバーの色の変更
- メールアドレスの変更（変えたい人は、新しいアカウントを作り直す）。パスワードの変更の画面（再設定で代える。REQ-029）
- 利用者一人ひとりの行動の追跡（利用状況は集計だけを見る。NFR-010）
- 運営者用の管理画面（ダッシュボード）。多くの人に使ってもらえるかを確かめるため、MVP の次に作る（NFR-014、Q-030）
- 自動の定期バックアップと、利用者が削除したデータの復元（NFR-017）
- 広告。友達以外にも使われ始めてから検討する（Q-029）。入れるときは、プライバシーポリシー（NFR-008）に送り先などを書き足し、外部送信規律への対応を確かめる。画面は、あとから広告を置く場所を足せる余地を残しておく
