# 読み直し（全体を取り直す）と、届く変更（リアルタイム）を両方使う画面では、読み直しの途中に届いた変更を入れ直す

## 何が起きたか
2026-10-26 に画面を部屋につないだ（5-2）。画面は、部屋から届く1件ずつの変更（付け外し）を地図に入れるほかに、「取り直して」や知らないメンバーの変更が届いたときに、グループ全体を API から読み直す。`/code-review` で、読み直しが飛んでいる間に届いた変更が、読み直しの結果で上書きされて消えると指摘された。例えば、新しく参加した人の変更で読み直しが始まった直後に、別の人が大阪を塗る。その変更は画面に入るが、その後に、大阪を塗る前に D1 を読んだ読み直しの結果が戻り、大阪が消える。次に読み直すまで食い違う。

## 原因
- 読み直しの結果を「いちばん新しい正しい状態」とみなして、そのまま置き換えていた。読み直しは、送った時点の少し前の写真で、戻るまでの間に届いた変更は写っていない

## どうしたか
- 読み直しを始めてから結果が戻るまでに届いた変更を覚えておき、結果に届いた順で入れ直してから画面に置く（`web/src/group/calc.ts` の `withRoomVisits`・`RoomVisitLog`）。読み直しが重なっても、それぞれ「自分を始めた後」の分を入れる。テストを書いた
- 別の問題として、部屋が配る順番が D1 に書いた順番と同じとは限らないことも分かった。こちらは MVP では受け入れ、architecture の「部屋が配るもの」に限界として書いた

## 次にどうするか
- 全体を取り直す仕組みと、1件ずつ届く仕組みを組み合わせる画面では、「取り直しの途中に届いたもの」をどう扱うかを先に決める（覚えて入れ直す、または取り直しの後にもう一度取り直す）
- 似た場面：送っている途中の仮の表示（失敗したら戻す）と、届いた変更が重なるとき。戻す先は「最後に保存できた状態」に届いた変更を入れたものにする（screens の「行った」の付け外し）
