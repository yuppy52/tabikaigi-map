# データベースで守る値は、その値に届く道（別の列の書き換え、型）を全部ふさぐ

## 何が起きたか
2026-10-12 に D1 のテーブル定義（`migrations/0001_init.sql`）を data-model のとおりに作り、制約のテスト31件が通った。そのあと `access-reviewer`（相当）に見てもらうと、中の指摘が5件出た。どれも実際に SQL を流して通ってしまうことを確かめたもの。
- 作成者の印（`is_owner`）の書き換えはトリガーで断っていたが、`group_id` は書き換えられた。作成者のメンバーを、作成者がいなくなったグループに移せば、作成者を作り直せた（NFR-006 (4)）
- 紐づけは「`uid IS NULL` のときだけ書く」API の `WHERE` だけで守っていて、紐づいた後の `uid` を別のアカウントに付け替えたり空にしたりできた。10グループのトリガーも `OLD.uid IS NULL` のときしか数えないので、付け替えでは上限も抜けた（NFR-006 (3)(13)）
- `CHECK (pref BETWEEN 1 AND 47)` は `13.5` を通した。主キー `(member_id, pref)` では `13.5` と `13.25` が別の行になり、1人で何行でも書けた（無料枠を使い切られる）。名前の列にはバイナリの値も入った
- 作成者は1人までの部分 `UNIQUE` は、テストが定義の文字列を見ているだけで、断ることを確かめていなかった

## 原因
- 守りたい値（作成者、紐づけ）を、その値の列の書き換えだけで考えていた。値の意味は「どのグループの」「どのアカウントの」と別の列との組で決まるので、組の相手の列を書き換えても同じことが起きる
- 「紐づいた後に書き換える操作はない」ので、API の `WHERE` で足りると考えていた。操作がないことは、データベースで断っても困らないことでもある
- SQLite は列の型を厳しく見ない（`INTEGER` の列に小数も文字も入る）。`CHECK` の範囲だけでは整数かどうかを確かめられない
- 先にトリガーで止まるので、その後ろの索引が本当に効くかを試せなかった

## どうしたか
- `id`・`group_id`・`is_owner`・`created_at` の `UPDATE` を断るトリガー、紐づいた `uid` の `UPDATE` を断るトリガー、20人のトリガーを足した。正しい流れ（紐づけ、名前の変更、退出、退会、グループの削除）が通ることもテストした
- 整数の列は `typeof(…) = 'integer' AND …`、文字の列は `typeof(…) = 'text' AND …` にした。JavaScript の `13` は整数として入ることも確かめた
- 部分 `UNIQUE` は、テストの中でトリガーを外して確かめ、`finally` で元に戻した。**`@cloudflare/vitest-plugin` 1.4 では、テストごとにデータベースが元に戻らない**（同じファイルのテストは同じ D1 を使う）ことを、この時に確かめた
- テストは47件になった。data-model・permissions の「守る場所」も直した

## 次にどうするか
- データベースで守る値ごとに、「その値の列」「組になっている列（グループ、アカウント）」「行を消して入れ直す」の3つの道で書き換えられないかを見る。書き換える正しい操作がない列は、トリガーで書き換えを断る
- 整数・文字の列の `CHECK` には `typeof` を入れる
- 2つの守りが重なっているとき（トリガーと索引）は、後ろの守りも単独で効くことをテストする。データベースを変えるテストは、元に戻す
- 制約を作ったら、push の前に `access-reviewer` に見てもらう
