# 守りを確かめる手順は、その道具が本当にその形で送るかを確かめて書く

## 何が起きたか
S-6c で、deploy の「最初のデプロイ」の 7 に、WAF のすり抜けを確かめる手順として `curl` で `/api/rooms/../health` を送る、と書いた。`/code-review` で、curl は送る前に `..` を縮める（実際には `/api/health` を送る）ので、この確かめは何も試さずに通ってしまう、と指摘された。

## 原因
「この URL を送れば試せる」と考え、道具（curl）がその URL を手を加えずに送るかを確かめなかった。

## どうしたか
手順に `--path-as-is`（パスをそのまま送る）を付けると書いた。

## 次にどうするか
- すり抜けの形（`..`、大文字、`%61` のような書き換え、重なったヘッダー）を確かめる手順を書くときは、道具が送る前に形を直さないかを確かめ、要る指定（curl の `--path-as-is` など）を添える
- 「止まった」だけでなく、止まったのが狙った形の要求だったか（管理画面のイベントに出たパス）も見る手順にする
