# 「画面が持つ」「作るときに決める」と書いた値は、実装の項目を小分けにするときに探して先に決める

## 何が起きたか
2026-10-21 に、Phase 2 の 3-3（地図の部品）が終わった。次の 3-4（グループの画面）に進む前に、メンバーの10色が決まっていないことに気づいた。data-model の「色」には、「10色（2026-10-10 にユーザーと決めた）。番号 0〜9 と実際の色の対応は画面が持つ」とだけ書いてあり、色そのものはどこにも書いていなかった。ユーザーからは「設計の段階で決まってなかったのかよ」と言われた。

## 原因
- 基本設計では「D1 に何を持つか」を決めるのが目的だった。そのため、色は番号だけを決め、色そのものは「画面が持つ」として先送りした。この先送りを、未決事項（open-questions）にも、画面の設計（screens）にも書いていなかった
- 2026-10-19 に Vite＋React の項目を小分けにしたとき（3-1〜3-5）、各項目が頼る設計書の値が決まっているかを見なかった。`coder` は「決まっていないことに当たったら止まる」決まりなので、止まって気づくことはできた。ただ、実装の途中で止まると、聞くのが遅くなる

## どうしたか
- 3-4 の前にユーザーに聞き、モックの6色に推奨の4色を足して決めた。黄色は「全員まだの県」の強調と見分けにくいので入れない（2026-10-22、data-model の「色」に表で書いた）
- 設計書で、先送りの書き方（「画面が持つ」「Phase 2 で決める」「作るときに書く」）を `grep` した。残っているのは次の4つ。どれも、それを作る項目の前に決める
  - 問い合わせの表の形（data-model）
  - レート制限の回数（architecture。本番で測ってから）
  - トップの文面（screens）
  - 色（今回決めた）

## 次にどうするか
- ロードマップの項目を小分けにするときは、各項目が頼る設計書の節を開く。そのうえで、先送りの書き方（「画面が持つ」「〜で決める」「作るときに書く」「仮の値」）を `grep` し、その項目で要る値が決まっているかを見る。決まっていなければ、小分けの中に「先にユーザーと決める」と書き、その項目を始める前に聞く
- 設計で値を先送りするときは、「画面が持つ」とだけ書かず、open-questions に Q を立てるか、「どの項目の前に決めるか」を書く
