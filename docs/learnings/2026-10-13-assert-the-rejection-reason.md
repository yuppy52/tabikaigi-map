# 「断られる」テストは、狙った理由で断られたことまで確かめる

## 何が起きたか
2026-10-13 の API のテストで、`access-reviewer` から「別の理由で通っている」テストを2つ指摘された。
- 「確認待ちの人は書けない」のテストが `status 401` だけを見ていた。トークンの誤り（`invalid_token`）でも 401 なので、テスト用の署名が壊れても通ってしまい、「確認待ち → ログインなし → `login_required`」の道を通ったかを確かめられていなかった
- 「形の違うグループIDは、D1 を引かずに 404」のテストは、入口の確かめを消しても、D1 を引いた結果の 404 で通ってしまう

前日（2026-10-12）の D1 の制約のテストでも、`/UNIQUE/` だけで合わせていて、どの制約で断られたかを区別できないと指摘されていた。

## 原因
- 「断られた」ことだけを確かめ、「どの守りで断られたか」を確かめていなかった。守りが何重にもあると、狙った守りが消えても、別の守りで断られてテストが通り続ける

## どうしたか
- 応答は `status` と `error` の値をまとめて `toEqual` で確かめた
- 入口の確かめは、テストの中で D1 の表の名前を一時的に変えて壊し、それでも 503 でなく 404 になる（D1 を引いていない）ことで確かめた（最後に元に戻す）

## 次にどうするか
- 断られるテストは、`error` の値（D1 の制約なら、制約の列の名前やトリガーの名前）まで確かめる
- 守りが重なっているときは、後ろの守りを外したり壊したりして、狙った守りだけで断られることを確かめる（[2026-10-13-guard-every-path-to-protected-value.md](2026-10-13-guard-every-path-to-protected-value.md) の「後ろの守りも単独で効く」と同じ考え）

2026-10-13：ユーザーの OK をもらい、.claude/rules/api.md の「テスト」に反映した。

## 追記（2026-10-13）：断られる人を「一番惜しい人」で選ぶ

### 何が起きたか
紐づけ・管理の操作の API のテストで、`access-reviewer` から次の指摘を受けた。「作成者のみ」や「管理できる人の変更」で断られる人として使っていたのは、ログインなしの人と、どこのグループの作成者でもない人だけだった。そのため、作成者かを確かめる SQL から `group_id = ?2` が抜けても、テストは通ってしまう。グループは誰でも作れて作成者になれるので、抜けたら誰でも他人のグループを消せる、という重大な抜けを見張れていなかった。よそのグループのメンバーの番号を消すテストと、作成者本人の uid で確認待ちの証明書のテストも、同じ理由で足りなかった。

### 原因
- 「断られる人」を、条件のどれにも当てはまらない人（まったく関係のない人）で選んでいた。そういう人は、条件の一部が壊れても、残りの条件で断られる

### どうしたか
- 条件の1つだけが違う人を足した：別のグループの作成者、同じグループの作成者でないメンバー、作成者本人の uid で確認待ちの証明書、よそのグループのメンバーの番号
- コードから `group_id = ?2` をわざと消してテストを流し、足したテストが4件落ちることを確かめてから元に戻した

### 次にどうするか
- 断られるテストの人は、守りの条件（誰の・どこの・確認済みか）を1つずつ外した「あと一歩で通りそうな人」で選ぶ
- 守りのテストを書いたら、守りの条件をわざと1つ消して、テストが落ちることを確かめる
