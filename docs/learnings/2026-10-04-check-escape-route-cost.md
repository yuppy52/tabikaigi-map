# 「困ったら移せばよい」という逃げ道は、移すときの費用と影響を確かめてから推す

## 何が起きたか
ADR 0003 の最初の推奨は「MVP は Firebase 一式。Hosting の転送量が心配になったら、画面の配信だけ Cloudflare に移す（移す作業は小さい）」だった。`doc-reviewer` から重大の指摘を受けた。`*.web.app` のまま始めて Cloudflare に移すとドメインが変わり、ブラウザに覚えた内容（端末が覚えたメンバー、匿名のログイン）が引き継がれず、ログインなしの人が全員入り直しになる。しかも移すきっかけは「Hosting の転送量が尽きそう」なので、尽きた後は古いURLからの転送も止まる。

## 原因
- 移す先（Cloudflare）の作業量だけを見て、利用者への影響（ドメインが変わる）を見ていなかった
- 逃げ道は「使うときには困っている」状況で使うのに、その状況で逃げ道そのものが使えるかを考えていなかった

## どうしたか
- 「独自ドメインを最初から取る」を推奨に加えた。ドメインが変わらなければ、配信先を DNS の付け替えだけで移せる。ユーザーと相談し、年約1,650円の `.com` を取ることにした（NFR-020）

## 次にどうするか
- ADR で「あとで〜に移せる」と書くときは、(1) 利用者に見えるもの（URL、ログイン状態、端末に覚えたもの）が変わるか、(2) 移すきっかけになる状況で、移す手段がまだ使えるか、(3) 移すための準備を最初にしておけば安くなるか（例：独自ドメイン）、の3つを書く
