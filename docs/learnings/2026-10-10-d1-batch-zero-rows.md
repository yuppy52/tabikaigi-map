# D1 の batch は「0行だった」では取り消されない。後ろの文は前の文の成功を自分で確かめる

## 何が起きたか
data-model を案 C で書き直したとき、紐づけを1つの batch で (1) アカウントの行を作る → (2) G を U に足す → (3) メンバーの「行った」を消す → (4) `UPDATE members SET uid = ? WHERE … AND uid IS NULL`（条件付き）の順に書いた。「1つの batch なので、途中で断られたら全部取り消される」と考えていた。
`/review-docs`（2026-10-10）で重大の指摘を受けた（#1）。(4) が条件に合わず0行でも、エラーではないので batch は成功し、(2)(3) は確定する。10グループの上限や「他の人が先に紐づけた」で断ったのに、メンバーの「行った」が消え、アカウントの「行った」には G が足されてしまう。グループを作る batch（グループを入れる → 上限を条件にメンバーを入れる）にも同じ形があった。

## 原因
batch（D1 の `db.batch()`）が取り消すのは、どれかの文が**エラー**になったときだけ。条件付きの `UPDATE` や `INSERT … SELECT … WHERE` が0行なのは「条件に合う行がなかった」という正常な結果で、エラーではない。「判断を SQL の `WHERE` に入れる」（D1 にはトランザクションがないための書き方：spike で確かめた）と「batch でまとめて取り消す」を組み合わせたとき、`WHERE` で断った結果が batch に伝わらないことを見落としていた。
（SQL の仕様からの判断。0行のときに後ろの文が動くことは、Phase 2 のテストで確かめる）

## どうしたか
- 紐づけは、紐づける文を先に置き、後ろの文には `WHERE EXISTS (SELECT 1 FROM members WHERE id = ? AND uid = ?自分)` を付けて、紐づけが成功したときだけ動くようにした
- 断りたい場面（10グループの上限、作成者の印の後付け）は、トリガーの `RAISE(ABORT)` でエラーにして、batch ごと取り消す形にした（D1 でトリガーが使えるかは要確認。使えなければ API で読み直して分ける）
- data-model の「考え方」に、この落とし穴を1項目として書いた

## 次にどうするか
- batch の中に条件付きの文（`WHERE` で断るもの）を書いたら、「それが0行のとき、後ろの文はどうなるか」を必ず考える。後ろの文に前の文の結果を確かめる条件を付けるか、断る場面をエラー（制約・トリガー）にする
- 断る理由を利用者に伝えたいとき（上限、満員、他の人が紐づけ済み）は、0行のあとに読み直して分ける
- テストに「条件付きの文が0行のとき、batch の残りが何もしない」を入れる
