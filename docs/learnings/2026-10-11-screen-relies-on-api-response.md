# 画面の分岐が頼る応答（404 など）を、API と SQL の設計が本当に返すかを確かめる

## 何が起きたか
Q-020 で screens に「開いている画面で、グループや自分のメンバーが消されていたら、書き込みが 404 になるので、知らせて移る」と書いた。`/review-docs`（2026-10-11、21件）で重大の指摘を受けた（#1）。
- 「行った」の付け外しは `INSERT … WHERE EXISTS`・`DELETE … AND EXISTS` で書くので、グループやメンバーが消えていても0行で「成功」になり、404 は返らない
- ログインしている人の付け外しは `account_visits` に `uid` で書くので、グループが消えていても成功する
- 削除は部屋から配っていなかった（architecture の「配らない」）

会議中に誰かがグループを消すと、ほかの人は塗り続け、保存できたように見えるのに、誰にも残らない。

## 原因
画面の知らせを書くときに、「消えていれば 404 が返るはず」と一般的な Web API の感覚で置き、data-model の SQL（0行は正常な結果）と architecture の配る表を開いて確かめなかった。[D1 の batch の0行](2026-10-10-d1-batch-zero-rows.md) と同じ「0行は成功」が、batch の外（画面への応答）でも起きた。

## どうしたか
- data-model に「0行だったら読み直して、グループがない・メンバーがいないは 404、紐づいていれば 403 を返す」を足した。ログインしている人の付け外しは、開いているグループに自分のメンバーがいるかも確かめる
- ユーザーと決めて、メンバーとグループの削除も部屋から「取り直して」を配るようにした（architecture）
- 503 も「枠切れ」と「一時的な失敗」で理由を分けて返すことにした（画面の文を分けるため）

## 次にどうするか
- 画面の設計に「〜が返ってきたら」「〜が届いたら」と書いたら、その応答を返す場所（data-model の SQL と API の決まり、architecture の配る表）を開いて、本当にその場面で返るかを確かめる。返らなければ、同じ変更の中で API の側に決まりを足す
- 条件付きの書き込み（`WHERE EXISTS`、`uid IS NULL` など）は、0行のときに画面へ何を返すかまで決める

## 仕組みへの反映
`.claude/agents/doc-reviewer.md` の「抜け漏れ」に2項目（画面が頼る応答、遷移図の立場と出口）を、`.claude/rules/docs.md` の「図」に画面遷移図の1行を足した（2026-10-11、ユーザーの OK）。
