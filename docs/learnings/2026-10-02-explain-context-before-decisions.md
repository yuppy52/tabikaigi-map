# 論点は、背景と具体的な場面を説明してから決めてもらう

## 何が起きたか
open-questions の Q-001〜Q-004 を、選択肢と短い説明だけで4問まとめて聞いたところ、ユーザーに閉じられた。「関連している事項を説明しながら決めたい。さっきのだけでは判断しづらい」とのことだった。
関係の深い論点をまとめ、前提になっている仕組みと、友達グループの具体的な場面（「たろうのスマホが『旅行部では s1 のたろう』と覚えていて…」）を説明してから聞き直すと、ユーザーは仕様の確認（「管理者って名前を変えられる仕様だっけ？」）や、別の案（「名前の変更はログインありの本人だけにする」）を出しながら決められた。

もう1つ、requirements の「1つのグループの中で名前は重複させない」という一文が「ログインなしで使う」の節に入っていたため、ユーザーは「ログインなし同士だけの決まり」と覚えていた。ユースケースでは全員の決まりとして書いていたので、決め直すことになった。

## 原因
- 論点は前提となる仕組み（端末が何を覚えているか、枠の使い回し、管理できる人の範囲）に依存しているのに、その説明を省いていた。選択肢のちがいが、利用者から見て何が起きるかとして伝わっていなかった
- 全員に当てはまる決まりを、特定の使い方の節の中に書いていた

## どうしたか
論点を「端末が覚えている名前」「メンバーの名前」「作成者とグループの後始末」のまとまりに分け、まとまりごとに背景 → 場面 → 推奨案とその理由 → 質問、の順で進めた。名前の重複は、2つの方針を場面つきで並べ直して決めた（全員重複させない）。

## 次にどうするか
- ユーザーに論点を決めてもらうときは、関係の深い論点をまとめ、前提の仕組みと具体的な場面を先に説明する。1回に聞くのは、説明したまとまりの分だけにする
- ユーザーの答えが今の仕様とちがう前提に立っていたら、どこにどう書いてあるかを示して、決め直すかを聞く
- requirements では、全員に当てはまる決まりを、特定の使い方（ログインなし／あり）の節の中に書かない。共通の節に置く

反映：1つ目を CLAUDE.md の「進め方」に、3つ目を `.claude/rules/docs.md` の「言葉」に足した（2026-10-02）。

## 再発（2026-10-10）
- `/review-docs` の24件を、1つの表（指摘・推奨）と「決めてほしいこと A〜D」で見せた。A（リアルタイム）は場面を添えたので決まったが、B（決定の基準）・C（ログと保存期間）・D（Firebase の初期設定）は「理解できていない」と言われた
- 2回目に「前提（何のための仕組みか）→ 何が問題か（具体的な場面）→ 提案」の順で書き直すと、D は画面を見て確かめてもらえた。B・C は「理解した気がしないが、それでいい」だった
- 次は、決めてほしい論点ごとに、最初から「前提 → 困る場面 → 提案」で書く。「決定の基準」「保存期間」のような言葉だけの見出しにしない。数が多いときは、1回に聞く論点を減らす
