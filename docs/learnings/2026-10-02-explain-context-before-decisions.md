# 論点は、背景と具体的な場面を説明してから決めてもらう

## 何が起きたか
open-questions の Q-001〜Q-004 を、選択肢と短い説明だけで4問まとめて聞いたところ、ユーザーに閉じられた。「関連している事項を説明しながら決めたい。さっきのだけでは判断しづらい」とのことだった。
関係の深い論点をまとめ、前提になっている仕組みと、友達グループの具体的な場面（「たろうのスマホが『旅行部では s1 のたろう』と覚えていて…」）を説明してから聞き直すと、ユーザーは仕様の確認（「管理者って名前を変えられる仕様だっけ？」）や、別の案（「名前の変更はログインありの本人だけにする」）を出しながら決められた。

もう1つ、requirements の「1つのグループの中で名前は重複させない」という一文が「ログインなしで使う」の節に入っていたため、ユーザーは「ログインなし同士だけの決まり」と覚えていた。ユースケースでは全員の決まりとして書いていたので、決め直すことになった。

## 原因
- 論点は前提となる仕組み（端末が何を覚えているか、枠の使い回し、管理できる人の範囲）に依存しているのに、その説明を省いていた。選択肢のちがいが、利用者から見て何が起きるかとして伝わっていなかった
- 全員に当てはまる決まりを、特定の使い方の節の中に書いていた

## どうしたか
論点を「端末が覚えている名前」「メンバーの名前」「作成者とグループの後始末」のまとまりに分け、まとまりごとに背景 → 場面 → 推奨案とその理由 → 質問、の順で進めた。名前の重複は、2つの方針を場面つきで並べ直して決めた（全員重複させない）。

## 次にどうするか
- ユーザーに論点を決めてもらうときは、関係の深い論点をまとめ、前提の仕組みと具体的な場面を先に説明する。1回に聞くのは、説明したまとまりの分だけにする
- ユーザーの答えが今の仕様とちがう前提に立っていたら、どこにどう書いてあるかを示して、決め直すかを聞く
- requirements では、全員に当てはまる決まりを、特定の使い方（ログインなし／あり）の節の中に書かない。共通の節に置く

反映：1つ目を CLAUDE.md の「進め方」に、3つ目を `.claude/rules/docs.md` の「言葉」に足した（2026-10-02）。

## 再発（2026-10-10）
- `/review-docs` の24件を、1つの表（指摘・推奨）と「決めてほしいこと A〜D」で見せた。A（リアルタイム）は場面を添えたので決まったが、B（決定の基準）・C（ログと保存期間）・D（Firebase の初期設定）は「理解できていない」と言われた
- 2回目に「前提（何のための仕組みか）→ 何が問題か（具体的な場面）→ 提案」の順で書き直すと、D は画面を見て確かめてもらえた。B・C は「理解した気がしないが、それでいい」だった
- 次は、決めてほしい論点ごとに、最初から「前提 → 困る場面 → 提案」で書く。「決定の基準」「保存期間」のような言葉だけの見出しにしない。数が多いときは、1回に聞く論点を減らす

- 作成者の持ち方を「メンバーに印（推奨）／グループに番号」の2択で聞いたら、「メンバーに持たせると最大10個作成者を持つってこと？」と聞き返された。具体的な表（メンバーの行の例）で説明し直すと決まった

- 中・軽の指摘を「#4〜#26 をすべて直してよいか」と番号でまとめて聞いたら、「具体的にどこを指摘しているかわからない」と言われた。指摘ごとに「ファイル／いまの書き方／直した後」の表にすると、#16・#18・#22 に意見が出た（そのうち2つは、私の提案が前提を取り違えていた）
- 次は：
  - 技術の言葉（トークン、ADR、トリガー、batch など）を論点に使うときは、最初に一言で何かを書く
  - 2択を聞くときは、選んだ後のデータや画面を、具体的な例（表の行、画面の文言）で見せる
  - レビューの指摘の扱いを決めてもらうときは、番号の範囲で聞かず、最初から「ファイル／いまの書き方／直した後」の表で見せる。ユーザーが表を見て意見を出せることが、取り違えを見つけるのにも役立つ

## 再発・3回目（2026-10-15、`/review-docs` の論点 C・D）
- C（満員のグループで、すでにいる名前を入れると「満員」が返る）を、結果だけで説明したら「なぜそうなるの？？」と聞かれた。D（退会の後に、ほかの端末に残る ID トークン）は、場面を1文で書いただけで「よくわからない」と言われた
- C は、参加の SQL の判断の順番（①人数を見る → ②同じ名前を見る、①で止まると②まで進まない）をコードで見せ、D は「通行証は端末ごと、API は署名と期限だけを見る」を前回の勉強会（第2回）につなげて、1つずつの手順で説明し直すと、どちらも決まった
- D で「案1は仕組みを増やすほどではない」と書いたら、「そんなにめんどくさい？DB への無駄なアクセスが増える感じ？」と聞かれた。実際は、表1つと SQL 3か所に条件を足すだけで、D1 とのやりとりも増えなかった。手間を大きく見せて、推奨に寄せていた
- 次は：
  - 「何が起きるか」だけでなく、「なぜそうなるか」（コードや SQL の判断の順番）を、最初の説明に入れる
  - 場面は1文にまとめず、「1. … 2. … 3. …」の手順で書く。前に説明した仕組み（勉強会の回）があれば、そこにつなげる
  - 推奨しない案は、手間を具体的に書く（表・SQL・テストがいくつ増えるか、DB とのやりとりが増えるか）。推奨の理由は手間ではなく、本当の理由（今回は「退会の後も uid が残る」「まれな場面のために部品が増える」）で書く

## 再発・4回目（2026-10-16〜10-19、開発運用と GitHub の設定）
- 開発運用の論点で、ユーザーから4回聞き返された
  - マイグレーションの決まり：「あまり理解できていない、具体例を出して説明してくれるとありがたい」
  - lint：「もう少し詳細を教えて。よくわからない」
  - Dependabot：「Dependabotは何？セキュリティを高めるのに必要なもの？」
  - 必須のチェックのやり方：「すまん。理解できないから説明してくれ」
- 最後の1つは、表に「ルールセット」「全体の上書き」「404」「strict」「Settings → Rules」を並べ、道具の言葉のまま比べていた。「守りの設定表が1枚ある → 3つ目の決まりを足したい → 欄がないと足せない → A は別の紙を1枚足す／B は表を書き写して差し替える」というたとえと、「どちらでも、できあがりの使い勝手は同じ」を先に書くと、すぐ決まった
- マイグレーションも、SQL の例と「表 → コード」の順番を手順で見せると決まった
- 次は：
  - 道具やサービスの設定（GitHub、Cloudflare、npm の道具）を決めてもらうときは、まず「それは何か」を一言で書く。次に、たとえ（紙、表、鍵など身近なもの）で仕組みを書く
  - 案の違いを書く前に、「できあがりの使い勝手が同じか、違うか」を書く。同じなら、違いは作り方と壊れるおそれだけだと先に言う
  - API の応答の番号（404）や HTTP の言葉（PUT、PATCH）は、決めてもらう文の中に入れない。要るなら理由の後ろに括弧で添える
