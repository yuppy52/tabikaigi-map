# Turnstile のない API は、よそのサイトから利用者のブラウザで呼ばせることができる。回数で何分もつかを数える

## 何が起きたか
2026-10-13 にグループの作成・参加・開く・「行った」の API を作り、`access-reviewer` に見てもらった。重大の指摘が1件出た：グループを開く `GET /api/groups/{id}` は Turnstile なしで呼べ、20人が47県を付けたグループなら1回で約1,000行を読む。D1 の読み取りの枠（1日500万行）は、IP ごとのレート制限の仮の値（10秒で50回）でも、1つの IP から約17分で尽きる計算だった。さらに、よそのサイトに `<img src="…/api/groups/ID">` を置けば、訪れた人のブラウザから IP を散らして読ませられ、IP ごとの制限が効かない。

## 原因
- 「使い切られる対策」（Q-031）は、1つの IP から続けて呼ぶ人を思い浮かべて決めていた。ほかの人のブラウザに呼ばせる道（画像、フォーム、事前の確認が要らない GET や POST）を考えていなかった
- 「Turnstile は作成・参加だけ、地図を開くたびには付けない」と決めたとき、付けない API が1回で何行読み書きするか、枠が何回で尽きるかを数えていなかった

## どうしたか
- 画面が必ず付ける目印のヘッダー（`X-Tabikaigi: 1`）がなければ、D1 を読まずに 400 にした。ブラウザは独自のヘッダーを勝手に付けず、付けるには事前の確認（preflight）が要り、その応答も D1 を読まない
- 1つの IP から何分で尽きるか（読み取り約17分、書き込み約3時間）を architecture に書き、本物の D1 で測り直すことを Phase 2 の確かめに足した。足りなければ応答を数秒キャッシュする案を試す

## 次にどうするか
- 確かめ（Turnstile、ログイン）のない API を作ったら、1回で読み書きする行の数と、無料枠が何回・何分で尽きるかを数えて、設計書に書く
- 利用者のブラウザから呼ばせる道（`<img>`、`<form>`、事前の確認が要らないリクエスト）でも呼べないかを見る。目印のヘッダーで、D1 に届く前に断る
- リアルタイムの部屋（WebSocket）はヘッダーを付けられないので、作るときに別の守り方を決める

2026-10-13：ユーザーの OK をもらい、access-reviewer の「使い切らせる」に反映した。

## 追記（2026-10-26：リアルタイムの部屋）
- 上の「部屋は作るときに別の守り方を決める」は、Origin が同じサイトでなければ断る（仮の値）にした。よそのサイトの `new WebSocket` は、ブラウザが Origin を付けるので断れる
- 部屋（Durable Objects）は、回数のほかに「動いている時間」（GB 秒）でも数える。`access-reviewer` に、自分でグループを1つ作れば、確かめが済んだ接続から文を送り続けて部屋を起こし続け、2部屋で1日の枠を使い切れると指摘された。部屋が捨てるだけのメッセージでも、届くたびに部屋が起きる。ほかに、1部屋に何千本もつなぐ、接続を少しずつずらして開いてアラームを何度も鳴らす、という使わせ方もあった
- 直したこと：画面が送らないはずのもの（ping 以外）が届いたら切る、1部屋100本まで、アラームは10秒に1回まで。それでも止めきれない分は requirements の「分かっている限界」に書いた
- 次から：時間で数える枠（Durable Objects、CPU 時間）を使うものは、「回数」に加えて「1つの正しい鍵（自分で作ったグループ）で、どれだけ長く起こしておけるか」を数える。受け取って捨てるだけの入力は、捨てずに接続を切る
