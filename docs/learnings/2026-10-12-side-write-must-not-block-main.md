# 記録のための書き込みを、本来の処理と同じ失敗の単位に入れない

## 何が起きたか
Q-025（利用状況の把握）で、「直近30日に開かれたグループ」を数えるために、グループを開く API の batch（読み取り）に `UPDATE groups SET last_opened_on = …` を足した。`/review-docs`（2026-10-12、24件）で重大の指摘を受けた（#1）。
- D1 の batch は、1文がエラーになると全部取り消される
- D1 の書き込みの枠（1日10万行）だけが尽きた日は、この `UPDATE` がエラーになり、読み取りまで失敗する。読み取りの枠（500万行）がまだ残っていても、全員が地図を「見る」こともできなくなる
- 書き込みを使い切るいたずらで、読み取りまで止められる

## 原因
- 運用のための記録（利用状況を数える）を、「1回の往復で済む」という効率だけで同じ batch に入れた。記録が失敗したときに本来の機能（開く）がどうなるかを考えなかった
- [D1 の batch の0行](2026-10-10-d1-batch-zero-rows.md) では「条件付きの文が0行のとき」を見たが、「1文がエラーのとき全部が取り消される」側を、新しい文を足すときに見直さなかった
- 無料枠は種類ごと（読み取り・書き込み・リクエスト）に別々に尽きる。片方だけが尽きた日を考えていなかった

## どうしたか
- 読み取りの batch とは別に、応答を返した後（`ctx.waitUntil`）に `UPDATE` を流し、失敗しても無視する形にした（data-model の「グループを開く」）
- テストに「この書き込みが失敗しても開ける」を入れることにした
- あわせて `last_opened_on` を空にしない形にした（作るときに日付を入れる）

## 次にどうするか
- 記録・計測・知らせのための処理（最後に使った日、件数、エラーの送信、ログ）を足すときは、「それが失敗したら、本来の機能はどうなるか」を書く。本来の機能を止めるなら、batch やトランザクション、同じリクエストの処理の流れから外し、失敗を無視する（ベストエフォート）
- 無料枠の上限は種類ごとに別々に尽きる前提で、「書き込みだけが止まった日」「外部サービスだけが止まった日」に、読む・見るができるかを確かめる
