# 手順や方針を新しく書く前に、同じ論点の要件がもう決まっていないかを探す

## 何が起きたか
2026-10-16〜10-17 に、デプロイの手順書（[deploy](../design/deploy.md)）を書いた。バックアップは「表を変えるときだけ取り、3つ残す」とユーザーに提案し、そのまま手順書に書いた。`/review-docs` で `doc-reviewer` から、次の指摘を受けた。
- [requirements](../requirements.md) の NFR-017 に、すでに「新しい版を出す前に毎回取り、直近の1つだけ残す」と決まっている
- その理由（利用者が消したデータが、運営者の手元に残り続けないため：NFR-008・[privacy](../design/privacy.md) の保存期間）にも反する

手順書は NFR-017 のとおりに直した（毎回取り、1つだけ残し、古いものは運営者が手で消す）。

## 原因
- 手順書を「運用の道具の使い方」として書き始め、要件（requirements）を開かなかった。バックアップは Phase 0 で要件として決めていたのに、手順書を書く時点では「これから決めること」だと思い込んでいた
- 決めたことを書いた後に、関係する文書を `grep` する決まり（[2026-10-04](2026-10-04-propagate-recommendation-flips.md)、[2026-10-10](2026-10-10-record-chat-decisions.md)）はあった。しかし、提案する**前に**、すでに決まっていないかを探す決まりはなかった

## どうしたか
- 手順書と ADR 0008 を NFR-017 に合わせて直した。ユーザーにも、提案の誤りとして伝えた

## 次にどうするか
- 手順書・設計・方針を新しく書く前、またはユーザーに案を出す前に、論点の言葉（例：バックアップ、保存期間、削除、ログ）で `docs/requirements.md` と `docs/design/` を `grep` する。決まっている要件があれば、それに従う
- 要件と違う案のほうが良いと思ったら、要件を黙って上書きせず、「NFR-xxx ではこう決まっているが、こう変えたい」と理由を添えてユーザーに確かめる。変えるなら要件の側も直す
- 提案には出どころ（決定済みの要件ID／推奨／仮の値）を添える（[2026-10-10](2026-10-10-record-chat-decisions.md) と同じ）

2026-10-19：ユーザーの OK をもらい、.claude/rules/docs.md の「決めたことの反映」に反映した。
