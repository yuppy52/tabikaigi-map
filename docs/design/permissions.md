# 権限マトリクス

状態：下書き（2026-10-10：requirements の REQ と NFR-006、[data-model.md](data-model.md) の「保存先で守るもの（NFR-006）との対応」をもとに、誰が何をできるかを1つの表にまとめた。新しく決めたことはない）

## この文書について

- 「誰が・何を・できるか」と「それをどこで守るか」を、操作ごとに並べる。決まりの正本は requirements の各要件で、ここはその一覧
- 「守る場所」の書き方：
  - **API**：Hono の API が、書き込む SQL の `WHERE` などで確かめる（形は [data-model.md](data-model.md) の「設計のポイント」）
  - **制約**：D1 の `UNIQUE`・`CHECK`・外部キー・トリガー
  - **画面**：画面だけの決まり。改造した画面なら破れる（破れても増える被害がないものだけ）
- 記号：○ できる、× できない、— その立場では起きない

## 人の区別

| 立場 | どういう人か |
|---|---|
| 招待URLを知っている人 | まだ参加していない人。グループIDを知っている |
| ログインなしのメンバー | 名前で入っている人。**確認待ちのアカウント**（メールの確認が済んでいない人）もここに入る（NFR-006 (10)） |
| 紐づいた本人 | ログインしていて（確認済み）、そのグループに自分のアカウントに紐づいたメンバーがいる人 |
| 作成者のメンバー | グループを作ったときの最初のメンバー（`is_owner = 1`）。ログインなしのままのことも、紐づいていることもある（REQ-052） |

### API から見える区別

API が確かめられるのは次の3つだけ。

1. グループID（URL に入っている）
2. 送られてきたメンバーの番号
3. 確認済みの ID トークンの `uid`（あれば）

ログインなしの人は証明書を持たないので、API では「ログインなしのメンバー」と「招待URLを知っている人」を見分けられない。そのため、ログインなしの人に許す操作は、API の上では「グループIDを知っている人なら誰でも」できる。招待URLを知っていれば参加して同じことができるので、増える被害はない（NFR-005 と同じ強さ。requirements の「分かっている限界」）。

## グループの外の操作

| 操作 | ログインなし（確認待ちを含む） | ログインしている人 | 守る場所 | 要件 |
|---|---|---|---|---|
| グループを作る | ○（作成者のメンバーになる） | ○（作成者のメンバーが最初から紐づく。10グループまで） | API（Turnstile：Q-031）、10グループは制約（トリガー） | REQ-001・REQ-060 |
| グループ一覧を見る | × | ○（自分に紐づいたメンバーがいるグループだけ） | API（`members` を自分の `uid` で引く） | REQ-032・REQ-034 |
| マイページ（アカウントの「行った」とメールアドレス） | ×（確認待ちの人に何を見せるかは Q-020） | ○（自分のものだけ。メールアドレスは画面が Firebase の SDK から読む） | Firebase Authentication、API | REQ-033・NFR-006 (2) |
| アカウントの「行った」を付け外しする | × | ○（自分のアカウントだけ） | API（自分の `uid` の行だけ書く） | REQ-030・NFR-006 (2) |
| 退会する | × | ○（自分のアカウントだけ。直前にログインし直す） | API（自分の `uid`、`auth_time`） | REQ-036・NFR-006 (6) |
| ほかの人のグループを探す・一覧する | × | × | 推測できないグループID、一覧する API を作らない | NFR-005・NFR-006 (7) |

| 操作 | 招待URLを知っている人 | ログインなしのメンバー | 紐づいた本人 | 守る場所 | 要件 |
|---|---|---|---|---|---|
| グループ名とメンバーの名前を見る | ○ | ○ | ○ | 推測できないグループID | REQ-002 |
| 地図（みんなの「行った」）を見る | ×（参加してから） | ○ | ○ | 画面。API はグループIDを知っていれば返す（「分かっている限界」） | REQ-002・NFR-006 (2)(7) |
| 新しいメンバーとして参加する | ○（20人まで。同じ名前は不可） | — | —（ログインしている人が参加すると、メンバーが紐づく。10グループまで） | 制約（`UNIQUE (group_id, name_key)`、`UNIQUE (group_id, uid)`、10グループのトリガー）、API（20人、Turnstile） | REQ-004・REQ-005・REQ-008・REQ-060・NFR-006 (8)(9)(11) |
| 紐づいていないメンバーとして入る（同じ名前を入れる） | ○（「この人として続けますか？」と確かめる。信頼ベース） | — | —（ログインしている人は「この人はあなたですか？」→ はいなら紐づける） | 画面（API はログインなしの人を見分けられない） | REQ-012・REQ-022・REQ-043 |

## 管理の操作

管理できる人（REQ-044）の設定ごとに分ける。「作成者のみ」が効くのは、`manage_by = 'owner'` で、かつ作成者のメンバーがいるときだけ（[data-model.md](data-model.md) の「作成者」）。

| 操作 | 「誰でも」（初期値） | 「作成者のみ」 | 作成者がいなくなった後 | 守る場所 | 要件 |
|---|---|---|---|---|---|
| メンバーを削除する（紐づいたメンバーも含む） | メンバーなら誰でも | 作成者のメンバーだけ（下の※） | 「誰でも」と同じ | API（`manage_by` と作成者を同じ SQL の `WHERE` で確かめる） | REQ-048・REQ-051・NFR-006 (5) |
| グループ名を変える | 同上 | 同上 | 同上 | 同上 | REQ-046・NFR-006 (5) |
| グループを削除する | 同上 | 同上 | 同上 | 同上 | REQ-047・NFR-006 (5) |
| 管理できる人を変える | ログインしている作成者だけ | ログインしている作成者だけ | 誰も変えられない | API（作成者のメンバーの `uid` が自分か。`email_verified`） | REQ-045・NFR-006 (4)(10) |
| 作成者を変える・付け足す | 誰もできない | 誰もできない | 誰もできない（作成者は戻らない） | 制約（部分 `UNIQUE` インデックス、`is_owner` の更新と後からの印付きの追加を断るトリガー） | REQ-051・REQ-052・NFR-006 (4)・[ADR 0005](../adr/0005-owner-flag-on-member.md) |
| 自分で退出する | ○ | ○（設定に関係なく） | ○ | 上の「退出する」 | REQ-049 |

※「作成者のみ」のときに通るのは：
- 作成者のメンバーが紐づいていれば、その本人（ログインしていて、`uid` が一致する）
- 作成者のメンバーが紐づいていなければ、作成者の名前で入った人（信頼ベース：REQ-052）。API の上では、作成者のメンバーの番号を送ってきた人になる

## 運営者

運営者は、`wrangler` で D1 を直接読み書きできる（アプリの権限の外）。使うのはバックアップ（NFR-017）、削除の依頼への対応（NFR-018）、集計（NFR-010）のときだけにする。

## 破られたときの影響（画面だけで守っているもの）

| 画面だけの決まり | 改造した画面でできること | 受け入れる理由 |
|---|---|---|
| 参加する前は地図を見せない（REQ-002） | 参加しないで地図を読める | 招待URLを知っていれば参加して見られる |
| 紐づいていないメンバーの「行った」は、その名前で入った人が付け外しする（REQ-023） | 参加しないで付け外しできる | ログインなしは信頼ベースで、同じ名前を入れれば誰でもできる |
| 「誰でも」のときの管理の操作はメンバーがする | 参加しないで削除・名前の変更ができる | 招待URLを知っていれば参加して同じことができる |
| ログインなしの作成者として操作する（REQ-052） | 作成者の名前で入らずに、作成者の番号を送れる | 作成者の名前を入れれば誰でも作成者として入れる |

どれも requirements の「分かっている限界」と同じ強さで、増える被害はない。
