# ADR 0005：作成者は、メンバーの行に付ける印（`is_owner`）で持つ

- 状態：**決定**（2026-10-10、ユーザーと決めた）
- 日付：2026-10-10
- [ADR 0003](0003-backend-selection.md) の「C で書き直すときの方針」のうち、**作成者**の項（`groups.owner_member_id` を `ON DELETE SET NULL` の外部キーにする）を置き換える。ADR 0003 のほかの部分は変わらない
- 関係する要件：REQ-001、REQ-037、REQ-045、REQ-051、REQ-052、NFR-006 (4)(5)、Q-019

## 背景

ADR 0003（案 C）では、作成者を「グループの行に、作成者のメンバーの番号（`owner_member_id`）を持つ」形にしていた。試作（[spike/migrations/0001_init.sql](../../spike/migrations/0001_init.sql)）でもこの形で、作成者のメンバーが消えたら番号が空になることを確かめた。

data-model を案 C で書き直すときに、この形には次の2つの弱さがあると分かった。

- `owner_member_id` には、**別のグループのメンバーの番号も入れられる**（外部キーはメンバーがいることしか確かめない）。防ぐには、複合の外部キーにするか、API のテストで守る必要があった（ADR 0003 にも「複合の外部キーにするか、API のテストで守る」と書いてあった）
- `groups` が `members` を指し、`members` も `groups` を指すので、表どうしが互いを指す（作るときに、グループ → メンバー → グループの番号を更新、の3段になる）

## 選択肢

| | A：グループに番号（`groups.owner_member_id`） | **B：メンバーに印（`members.is_owner`）** |
|---|---|---|
| 作成者が消えたとき | `ON DELETE SET NULL` で番号が空になる | 行と一緒に印も消える。何もしなくてよい |
| 別のグループのメンバーが作成者になる | 起きうる（API のテストか複合の外部キーで防ぐ） | 形の上で起きない（印はそのグループのメンバーの行にしか付かない） |
| 作成者が2人になる | 起きない（番号は1つ） | 部分 `UNIQUE` インデックス（`members (group_id) WHERE is_owner = 1`）で防ぐ |
| 作成者を後から付ける・付け替える | `UPDATE groups` で起きうる（API で防ぐ） | トリガーで `is_owner` の更新と、2人目以降の印付きの追加を断る（D1 で使えるかは要確認。使えなければ API のテスト） |
| 試したか | 試作で確かめた〔済：ローカル〕 | 未〔Phase 2 でテスト〕 |

## 決定

**B：作成者のメンバーの行に `is_owner = 1` を付ける。** 印はグループを作るときの最初のメンバーにだけ付け、後から付けたり外したりしない。「作成者のみ」が効くかは、`manage_by = 'owner'` かつ「`is_owner = 1` のメンバーがいる」で計算する（同じ事実を2か所に持たない）。

詳しい形は [data-model.md](../design/data-model.md) の「作成者」。

## 結果

- 良くなること：作成者が消えたとき（REQ-051）と、別のグループのメンバーを指す誤りを、データの形で防げる。表どうしが互いを指さない
- 残ること：部分 `UNIQUE` インデックスとトリガーが本物の D1 で動くかは要確認（D1 の公式に、部分インデックスの例はあるが `UNIQUE` 付きの例はなく、トリガーは明記がない：2026-10-10 に `researcher` で確認）。Phase 2 の最初に試し、動かなければ同じ決まりを API のテストで守る。その場合でも、この ADR の決定（B）は変えない
- 試作で確かめた「同じ名前で入り直しても作成者に戻らない」は A の形でのことなので、B の形で Phase 2 にテストし直す
