# ADR 0013：ログインをやめる。作成者と「管理できる人」の設定もなくす

状態：決定（2026-11-06。2026-11-09：`/review-docs` を受けて、ログインを戻したときに見えることを書き足し、スマホを替えたときの入り方を名前を選ぶ形（REQ-012）に合わせた）

- 関係する要件：なくした要件（REQ-013・REQ-014・REQ-027〜REQ-045・REQ-051・REQ-052・REQ-057〜REQ-060）、変えた要件（REQ-001・REQ-005・REQ-007・REQ-008・REQ-012・REQ-015・REQ-024・REQ-025・REQ-046〜REQ-050、NFR-002・NFR-006〜NFR-008・NFR-010・NFR-018）
- [ADR 0003](0003-backend-selection.md) の「認証だけ Firebase Authentication（Spark）」をやめる（ADR 0003 のその部分を置き換える。Cloudflare Workers・Hono・D1 はそのまま）
- [ADR 0005](0005-owner-flag-on-member.md)（作成者はメンバーの行の印で持つ）を置き換える。作成者そのものを持たない

## 背景

Phase 2（ログインなしで公開）の終わりが近づいた 2026-11-06 に、ユーザーから「ログイン機能をなくしたい。不正アクセスが多く、漏れたときに責任を持てない」と提案があった。

- ログインありは Phase 3 の予定で、画面には入口がない。ただし API（8つの入口）、D1 の表（`accounts`、`account_visits`、`members.uid` など）、ID トークンの確かめ（`jose`）は Phase 1 で作ってあった
- 本番にはまだ何も出していない。消えるアカウントも、引き継ぐデータもない
- 「先月の不正アクセス」がどの件かは確かめておらず、この判断の根拠にはしていない。根拠は、預かる情報と、運営者1人で受ける対応（乗っ取り、退会、確認メールの上限）を減らせること

## 選択肢

| | A：ログインをやめる（推奨・決定） | B：Phase 3 でログインを作る（いままでの予定） |
|---|---|---|
| 預かる情報 | メンバーの名前、グループ名、行った県、問い合わせ（返信先は任意）、記録 | 左に加えて、ログインのメールアドレス、パスワード（Firebase に置く）、Google の表示名と写真の URL |
| 運営者の対応 | 退会、確認待ちのアカウント、乗っ取り、確認メールの上限がなくなる | 左のすべてを受ける |
| 使う人の困りごと | 「行った」をグループごとに塗る（同期しない）、グループ一覧がない（招待URLから開く）、名前を変えられない（退出して入り直す）、「作成者のみ」で締め出せない | なし |
| 外部のサービス | Cloudflare、Sentry | 左に加えて Google（Firebase） |
| 作る量 | 減る（Phase 3 がなくなる。今ある API・表・テストを消す） | Phase 3 で画面と確かめを作る |

## 決定（2026-11-06 にユーザーが推奨どおりに選んだ）

1. **ログインの機能をやめる**。Phase 3 をなくす。要るようになったら、新しい ADR で足す（列と表を足せば戻せる。消したコードは git の履歴に残る）。ただし戻したときは、それまでに作られたグループに作成者がいないので、そのグループは誰でも管理できるままになる。公開の後は本番で流したマイグレーションを書き換えられないので、新しいマイグレーションで列を足す
2. **書いてあるログインのコードと表も、最初の本番のデプロイの前に消す**。使わない入口を本番に出さないため。マイグレーション `0001_init.sql` はまだ本番で流していないので、書き換えてよい（[deploy](../design/deploy.md) の決まりは、本番で流したものだけを書き換えない）
3. **作成者と「管理できる人」の設定もなくす**。ログインがないと本人を見分けられず、「作成者のみ」を守れない（REQ-045 はログインしている作成者だけが変えられる決まりだった）。メンバーの削除、グループ名の変更、グループの削除は、いつも誰でもできる
4. **問い合わせのフォームの返信先のメールアドレスは任意**にする。ログインをなくすと、アプリが預かるメールアドレスはここだけになるため。返事が要らない依頼や、アドレスを預けたくない人のため

## 結果と注意

- **責任はゼロにならない**。メンバーの名前、グループ名、行った県、問い合わせは残る。本名を入れる人がいるかもしれないので、入力の画面と使い方で「ニックネームでよい」と伝える（使い方とプライバシーポリシーの項目で文を決める）
- 招待URLを知っている人は、そのグループのメンバーの削除とグループの削除ができる。締め出す設定はない（requirements の「分かっている限界」）
- スマホを替えたときは、招待URLを開いて参加の画面で自分の名前を選べば、元のメンバーに入れる（REQ-012。2026-11-09 に、名前を入れて確かめる形から、名前を選ぶ形にした）
- 個人情報保護法の扱いは、公開の前の相談ダイヤルへの電話で、ログインなしの形として聞く
- 消すもの（コードの側。roadmap の「ログインをやめる」の小分け）：
  - API：ID トークンの確かめ（`api/src/firebase-auth.ts`）、アカウント（`api/src/account.ts`）、ログインの入口8つ、作成者・管理できる人の確かめ
  - D1：`accounts`、`account_visits`、`members.uid`・`is_owner`、`groups.manage_by`、それらのトリガーと索引
  - 部品：`jose`。設定：`wrangler.jsonc` の `FIREBASE_PROJECT_ID`
  - 画面：ログインと作成者の文、グループ設定の「管理できる人」
- 運営者は、コードを消した後に Firebase のプロジェクトを消す（作ってあるため）
