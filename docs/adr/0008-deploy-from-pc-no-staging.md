# ADR 0008：デプロイは運営者の PC から手で行い、ステージングは作らない

状態：決定（2026-10-16）

- 関係する要件：NFR-004（費用の上限）、NFR-014（運営者1人で回せる）、NFR-017（バックアップ）
- 手順の正本：[design/deploy.md](../design/deploy.md)

## 背景

Phase 2 から、本番（Cloudflare の Worker 1つと D1 1つ：[architecture](../design/architecture.md) の「環境」）にコードとテーブル定義を出す。決めることは2つある。

- **誰が、どこからデプロイするか**
- **テーブル定義の変更（マイグレーション）を、本番の前にどこで試すか**

前提となる仕組みは次のとおり。
- `wrangler deploy` で出したコードは、`wrangler rollback` で前の版に戻せる。ただし D1 のテーブルとデータ、Durable Objects の中身は戻らない（公式）
- テーブル定義の変更には「元に戻す」がない。間違えたときは、D1 の Time Travel で時刻を指定して巻き戻す（その時刻より後の書き込みも消える）か、直すための新しいマイグレーションを足す
- 表の変更とコードのデプロイは別々のコマンドで、間に数十秒〜数分のずれがある。そのため、変更の順番を守らないと、その間エラーになる（[design/deploy.md](../design/deploy.md) の例）

## 選択肢

### デプロイ

| | A：運営者の PC から手で | B：main へのマージで GitHub Actions が自動で |
|---|---|---|
| 流れ | マージした後、Claude が `npm run deploy`（型の確かめ → テスト → デプロイ）を実行する。実行の前に `ask` で OK をもらう | マージするとワークフローがデプロイする |
| 表の変更との順番 | 手順書の順番（バックアップ → 表 → コード）を人が守る | マージした瞬間にコードが出るので、表より先に出ないようにするには、承認を挟む設定（GitHub の environment）と、表の変更の自動化が要る |
| 鍵（Cloudflare の API トークン）の置き場所 | 運営者の PC の `.env`（リポジトリに入れない）だけ | GitHub の秘密の値。PC に加えて置き場所が1つ増える |
| 増える手間 | `package.json` のスクリプト1つ | ワークフロー1つ、environment の設定、表の変更の自動化 |
| 弱点 | デプロイを忘れると、本番が main より古いままになる | — |

### 試す場所

| | A：ステージングを作らない | B：ステージングを作る |
|---|---|---|
| 公開の前 | 本番そのものを試す場所にする（利用者がいないので、失敗したら D1 を作り直してよい） | 同じ |
| 公開の後 | 本番の書き出し（`wrangler d1 export`）を手元の D1 に読み込み、マイグレーションを当てて `wrangler dev` で確かめてから本番に当てる | ステージングの D1 に当てて確かめてから本番に当てる |
| 増えるもの | なし | `wrangler.jsonc` の2つ目の環境、2つ目の D1、サブドメイン（`staging.tabikaigi-map.com`）、他人に開かれないための Cloudflare Access の設定。無料枠をアカウントで本番と分け合う |
| 見つけられないもの | 本物の D1 でしか起きない違い。ただし、公開の前に本番で一度確かめる（roadmap の Phase 2 の〔未〕） | 少ない |

## 決定

**デプロイは A（運営者の PC から手で）、試す場所も A（ステージングを作らない）**。2026-10-16 にユーザーと決めた（どちらも推奨案）。

理由：
- デプロイ：表を変えるときは「バックアップ → 表 → コード」の順番を守る必要がある。B で同じ順番を守るには、承認の設定と表の変更の自動化を作り込む必要がある。MVP のデプロイは回数が少なく、順番を人が確かめるほうが確実。また、鍵を PC の1か所だけに置ける
- 試す場所：利用者がいない公開前は、本番で試しても困る人がいない。公開の後は、本番のデータの写しで手元で練習すれば、ステージングで見つかることの大半を見つけられる。ステージングの4つの設定と、無料枠の分け合いに見合わない

## 結果と注意

- 手順（デプロイ、マイグレーションの決まり、戻し方、鍵の作り方）は [design/deploy.md](../design/deploy.md) に書く
- マイグレーションの決まり（2026-10-16 にユーザーと決めた。2026-10-17：`/review-docs` を受けて制約を強める変更と表の作り直しを足した）：足す変更は「表 → コード」の順。消す・名前を変える変更はデプロイを2回に分ける。制約を強める変更は「違反を数えて直す → コード → 制約」。表を作り直すときは子の表も一緒に作り直す（親の表を消すと子の行が消えることを手元で確かめた）。バックアップは NFR-017 のとおり新しい版を出す前に毎回取り、1つだけ残す。表を当てる直前に Time Travel のブックマークを控える。本番に当てたファイルは書き換えない。公開（友達に最初の招待URLを渡した日）の前は D1 を作り直してよい
- 見直すとき：Phase 3（ログイン）で、戻せないと困る変更（アカウントの表など）が出てきたら、ステージングをもう一度考える。デプロイを忘れることが続いたら、B を考える
